# v0.11.4 — Architecture audit

Scope: `packages/core/**` (registry / install logic shared by desktop + CLI) and `packages/desktop/src/main/**` (IPC bridge). The CLI surface is excluded — the `cli-minimal` plan is queued to absorb pruning there.

**Method.** Mapped the export surface of every module reached from `packages/core/src/index.ts`, walked the IPC handler table in `packages/desktop/src/main/main.ts` (≈60 handlers), and applied the deletion test to suspected-shallow modules. The audit names *deepening opportunities* in [LANGUAGE.md](../../UBIQUITOUS_LANGUAGE.md) vocabulary (**Origin**, **Drift**, **Probe**, **Baseline**, **Bucket**, **Curation layer**, **Registry**). No architectural changes are applied here — the maintainer schedules follow-ups. The one exception: a single cosmetic dead-code removal that M5's sweep missed.

## 1. Untested contracts — top-five gaps

**There are zero `.test.ts` / `.spec.ts` files in `packages/core`.** Every contract below is exercised only through manual desktop runs. Tests would be the highest-leverage investment the next milestone can make — most of these modules are pure or near-pure and would test cheaply.

1. **`packages/core/src/heal.ts` — `hashSkillFolder`.** Determines whether the build sees **Drift** on a **Skill**. Behaviour is non-obvious in three places that aren't exercised: the 8 MB **HASH_BYTE_BUDGET** fallback (returns `null` → drift detection silently disengages); symlink hashing (link content, not realpath); the two sidecar exclusions (`.skills-bank.json`, `.skills-bank-hash`). Each is load-bearing for the **Drift** lifecycle and each fails silently if regressed.

2. **`packages/core/src/sync.ts` — `applyCanonicalSync` conflict-resolution branches.** Five paths (no-collision upsert; bundled→bundled overwrite; `keep-mine`; `use-canonical`; `rename-mine`) and one orthogonal preservation rule (the **meta.json tags** are read pre-overwrite and spliced post). Tag preservation is a regression-prone seam — a single typo would silently nuke every user's local tag edits on the next sync, with no UI signal. No test pins it.

3. **`packages/core/src/merge.ts` — `mergeImportRegistry`.** Same conflict-resolution surface as Sync but with subtly different semantics (merged-in **Skill**s are stamped `source: yours` rather than `bundled`, the rename suffix scheme is reused but the canon-cache invalidation is only triggered on this path). Two near-duplicate code paths with divergent semantics is exactly the shape that drifts without a test pinning the difference.

4. **`packages/core/src/upstream.ts` — `mirrorSkillFolder` partial-failure invariant.** The function fetches every blob *before* wiping `destDir`, so transport errors mid-loop leave the local **Skill** intact. That invariant — "no disk mutation on partial fetch failure" — is the entire safety story of the direct-fetch **Update** path. A test simulating one failing blob (last-blob-fails is the worst case) would lock it down.

5. **`packages/core/src/skill-state.ts` — `classifyDrawerState` heal-state branching.** The classifier is pure, ~250 lines, and is the single source of truth for which **Origin operations** the drawer offers. The fan-out around `entry.drift === true` + `entry.source.upstream?.kind === "github"` (the `user-edited-with-upstream` vs `bundled-skill-edited` split) is the load-bearing rule. Table-driven tests over each `DrawerState` ↔ `PrimaryAction` ↔ capability triple would be cheap and would catch any future capability-flag drift.

(Honorable mention: `applyRegistration` in `import.ts` — five action arms, real-dir vs symlink-mode adoption, sweep-and-converge logic across every agent dir. Tested only via manual install flows.)

## 2. Consolidation candidates — top three

1. **`heal.ts` + `source.ts` + `canon.ts` are a single domain: the on-disk Skill state record.** All three read/write sidecars (`.skills-bank.json`, `.skills-bank-hash`, `<state>/upstream-canon.json`) and together encode the full **Baseline** + **Origin pointer** + canon-membership tuple. Today they're three modules without a unifying interface, and consumers in `build.ts` and `sync.ts` reach into each individually. Deletion test: collapsing them under a **SkillRecord** module concentrates the "what does an on-disk skill *know about itself*" question into one place. Today, finding all writes to a **Skill**'s sidecars requires grepping three files.

2. **`packages/desktop/src/main/main.ts` is 2,906 lines.** It owns: registry-root resolution, `AppConfig` persistence, **Probe** scheduler + repo cache, direct-fetch **Update** implementation, the discover-view embed, the IPC handler table (60+ handlers), the auto-updater wiring, the GitHub OAuth bridge, the diff engine (`computeFolderDiff` + `walkFiles` + `looksBinary`). Several of these are pure functions wrapped in IPC and would extract cleanly:
   - **Probe scheduler** (`runUpstreamProbe`, `buildFolderHashMap`, `repoProbeCache`, `probedUpdates`, `augmentWithProbedUpdates`) → `packages/core/src/upstream-probe.ts`. It's currently in main only because of the `repoProbeCache` `Map`, which is just module-level state — equally welcome in core.
   - **Folder diff** (`computeFolderDiff`, `walkFiles`, `readTextIfSmall`, `looksBinary`, `DIFF_BYTE_BUDGET`) → `packages/core/src/diff.ts`. Pure, node-only, identical seam to `hashSkillFolder`.
   - **`applyUpstreamUpdate`** → belongs in core alongside `mirrorSkillFolder`. It's the "**Update** operation" in glossary terms; today it lives in main because it needs `getStoredToken` and `registryRoot`, both injectable.

3. **Conflict resolution is split across `sync.ts` and `merge.ts`.** Same `ConflictAction` enum, same rename-target resolver (`resolveRenameTarget` defined identically in both), same decision-application switch (`keep-mine` / `use-canonical` / `rename-mine`). The two callers diverge on which `source` to stamp (`bundled` vs `yours`) and which canon-cache to invalidate. A shared **applyConflictDecision(entry, decision, stampAs)** primitive would eliminate the duplication and pin the divergence in one parameter.

## 3. Extraction candidates — top three

1. **`build.ts` `computePublishStates` is a different concern than `buildRegistryIndex`.** It shells out via `execSync` to `git status` / `git rev-list` / `git log`. The rest of `build.ts` is pure file-walking. The git surface is the one thing in `build.ts` that *can* fail catastrophically (git missing from PATH, hostile repo states, large registry → slow). Extract to `packages/core/src/publish-state.ts` and let `buildRegistryIndex` take a `publishStates?: Map<…>` injection. Tests for the file-walker no longer have to stub `child_process`.

2. **`paths.ts` is the **Registry** state-dir locator, but the **Origin probe cache** state lives in `main.ts` module scope.** Probe cache TTL + persistence semantics are exactly the kind of thing that belongs alongside `getStateDir()` in core — both are "where does **app state about a Registry** live." Today the cache is non-persistent and rebuilt every launch; making it a `paths.ts`-style locator would unblock persisting it to disk between sessions (which the `bank-mode-persistence` plan will want anyway).

3. **`main.ts` `replaceRegistryWithRepo` (≈80 lines) is doing three things at once.** (a) Clone-or-pull the chosen GitHub repo into userData; (b) write the **Origin pointer** seed across every cloned **Skill** missing one; (c) flip `AppConfig.registrySource` + `linkedRepo`. Three concerns at three different layers (transport, **Origin** stamping, persisted config). The middle one is the only piece that needs glossary vocabulary; the other two are infrastructure. Splitting them gives the **Origin** stamper a real test surface (it currently runs only during repo-link).

## 4. ADRs the maintainer should write

`docs/adr/` does not exist. **Create it.** The following decisions are load-bearing and currently only documented in inline comments or plan files — future architecture reviews will re-suggest these without an ADR record.

1. **ADR-0001 — Why `packages/core` has zero tests, and what the entry criteria are.** The repo went from CLI → desktop while the canonical seam (core) stayed untested. State whether tests are deferred ("post-1.0") or actively in-scope, and which modules cross the bar first. This prevents every future architecture review from re-suggesting "add tests" without traction.

2. **ADR-0002 — Sidecar files are the **Skill record**.** Three sidecars (`.skills-bank.json`, `.skills-bank-hash`, optional `meta.json`) together carry **Source** + **Origin pointer** + **Baseline** + tags. Record the decision to keep them as separate files (vs unifying into one sidecar), the rationale (independent write paths from sync / heal / build), and the rule that no fourth sidecar is added without revisiting. This is the consolidation candidate #1's prior — the ADR makes it a real decision rather than accreted convention.

3. **ADR-0003 — Direct-fetch **Update** vs `npx skills update`.** The `origin-paradigm-reframe` plan landed this, but the *decision* (and the reasoning around npx-in-packaged-Electron being load-bearing-broken) lives only in commit messages and the plan file. An ADR pins it: when does the maintainer choose direct-fetch vs shelling out to a CLI, and what's the criterion for ever reversing? Today's `applyUpstreamUpdate` would re-acquire a load-bearing `npx` dependency on the next "let's just use the CLI" refactor without this guardrail.

## 5. Domain language gaps (internal identifiers)

M4 aligned user-visible copy. Internal identifiers lag behind the glossary in `UBIQUITOUS_LANGUAGE.md`:

- **`SkillSource.upstream` field name still says "upstream"** despite the glossary having made **Origin** canonical. Flagged in the glossary itself ("rename or alias for v0.12 if the user-facing rename to Origin sticks") — it has stuck. `SkillSource.origin` is the post-rename name; mechanical replacement across core + main.
- **`UpstreamPointer` → `OriginPointer`** (same reason). Used in `source.ts` and reached transitively through every `RegistryEntry.source` consumer.
- **`scanAndStampUpstreamFromLock`** is the one "stamp" identifier the glossary blesses (internal automatic write) — keep this one. But every other `upstream`-named function (`probeRepoTree`, `mirrorSkillFolder`, `applyUpstreamUpdate`) is a candidate for the **Origin** rename.
- **`acceptDriftKeepLocal` / `acceptDriftSeverUpstream` / `acceptDriftTakeCanonical`** (in `heal.ts`) are the three **Origin operations** in glossary terms: **Unlink origin** (sever), **Update** + drop-baseline (take canonical), and a hybrid (keep local — no glossary verb yet; might want one). The function names currently use the verbs the glossary retires ("accept", "sever", "take canonical"). Rename in the same v0.12 pass.
- **`bundled-skill-edited`** as a `DrawerState` value is the deprecated drift-state name flagged in the glossary; canonical is **Edited without origin** (or a programmatic variant). The user-facing string was already retired in M4; the internal enum value still ships.

These don't need to land mid-v0.11; they want a single coherent v0.12 rename pass with codemod + alias deprecation gate. Track in a follow-up plan: `docs/plans/origin-rename-pass.md`.

## 6. Applied — M5-overlap fix

- **`packages/core/src/import.ts` — removed dead `copyDir(src, dst)` function.** Defined once, only called from inside its own recursive body. Knip missed it because the self-reference satisfies the "used somewhere" check. Caught here by the deletion test ("if I delete this, what reappears?" → nothing; the only call site is itself). Pure cosmetic dead code.
