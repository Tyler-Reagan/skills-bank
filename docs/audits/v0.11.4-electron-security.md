# v0.11.4 — Electron security audit

Scope: `packages/desktop/src/main/main.ts`,
`packages/desktop/src/main/preload.mts`, `packages/desktop/src/main/auth.ts`,
`packages/desktop/src/shared/ipc.ts`, `packages/desktop/src/renderer/index.html`.

Audit dimensions: `contextIsolation`, `nodeIntegration`, IPC input validation,
file-path sanitization, OAuth-token storage, CSP, `sandbox`, remote-content
loading, dev-tools exposure, click-jacking / `window.open` hardening.

## Applied hardening (this PR)

1. **`openInFinder` path allowlist** — `main.ts:~2224`. Renderer-supplied paths
   are now validated to live inside `registryRoot` or one of the known agent
   skills dirs (`getAgentSkillsDir(...)` for each `AgentId`). Anything outside
   is silently refused and warned to stderr. Closes: a compromised renderer
   using `shell.openPath` as a generic file-open primitive on arbitrary
   filesystem paths.
2. **`openExternal` URL scheme allowlist** — `main.ts:~2794`. Only `http:` and
   `https:` URLs reach `shell.openExternal`. `file://`, `javascript:`, and
   registered custom URI handlers are dropped. Closes: a compromised renderer
   launching attacker-controlled local files or protocol-handler payloads via
   the OS shell.
3. **Main `BrowserWindow` `sandbox: true`** — `main.ts:~1205`. Brings the
   primary renderer in line with the Discover `WebContentsView`. The preload
   only imports `electron` (`contextBridge`, `ipcRenderer`) which are
   sandbox-compatible. Defense-in-depth against renderer RCE.
4. **App-wide `web-contents-created` hook** — `main.ts:~2873`. Default
   `setWindowOpenHandler` denies new windows and routes http(s) to
   `shell.openExternal`; default `will-navigate` cancels navigation outside
   `file://` and the Discover host allowlist. Catches any future contents we
   add without explicit per-contents wiring.
5. **`importRegistryMergeApply` source-path re-validation** — `main.ts:~2138`.
   The picker IPC normally hands us a vetted directory, but the apply call now
   re-checks `path.isAbsolute`, existence, directory-ness, and presence of a
   `skills/` child before invoking the fs-walking merge logic. Refuses
   arbitrary substituted paths from a misbehaving renderer.
6. **`discoverOpenTerminal` Windows command-string hardening** — `main.ts:~1074`.
   `cwd` (`registryRoot`) is stripped of `"`, `\r`, `\n` before interpolation
   into the cmd.exe string. `registryRoot` is user-set rather than network-
   sourced, so impact was low, but the quoting bug was real.

## Deferred — needs design decision

These are not clear wins; they trade off against current UX, packaging, or
maintenance cost and warrant a maintainer call rather than a unilateral
hardening commit.

### D1. Add a stricter, app-specific CSP

Current CSP allows `'unsafe-inline'` for styles because the renderer uses
inline `style` attributes from React + the design system. Tightening to a
nonce-based or hashed inline-style policy would require coordination with
the renderer build pipeline (Vite) and possibly a sweep of any inline
`<style>` usage. Worth it once the renderer's inline-style story is itself
audited and consolidated.

### D2. Replace `safeStorage` with `keytar` (or equivalent native keychain)

`safeStorage` is the documented Electron primitive and works well on macOS
(uses Keychain). On Linux without a libsecret-providing keyring (rare server-
y setups), `safeStorage` falls back to a basic obfuscation rather than true
encryption (Electron logs a warning to stderr). For a desktop app this is
acceptable; the user opt-out path is "don't sign in." If we ever ship a
mode where token possession alone is high-value (e.g., write-scope to
private repos), revisit. For the current `repo` scope on a user-installed
app this is in policy.

### D3. Encrypt `device-flow.json` at rest

`auth.ts:127-128` writes the mid-flow recovery state as plaintext JSON. The
file contains the GitHub device code (short-lived, ~15 min) and is rationalized
in code comments as low-value — interception alone doesn't grant a token, the
attacker also has to intercept the github.com side of the device-flow grant.
Encrypting via `safeStorage` would be one or two lines but would also break
the documented "user can inspect and clear" affordance. Leave as-is unless a
threat model surfaces.

### D4. Lock the `repo` OAuth scope down further

`auth-config.ts:34` requests `repo` because GitHub OAuth Apps don't offer a
finer-grained read-only scope for private repos. Plan-level mitigation: migrate
to a GitHub App with `Contents: read` permission. Tracked in the existing
GitHub-mode plans; out of scope for this audit.

### D5. Consider disabling `toggleDevTools` in packaged builds

`main.ts:~1170` includes `role: "toggleDevTools"` in the View menu, which
remains available in packaged builds. Pro: power-user diagnosability when a
production bug surfaces. Con: a social-engineering vector ("paste this into
the console") that's only blocked by user awareness. The current call is
that diagnosability wins. Revisit if a user-attacker report comes in.

### D6. Restrict `pickCustomSkillsDir` / `setRegistryRoot` to non-system roots

Both handlers let the user point the app at any directory the OS lets them
read. A confused-user attack ("set your registry root to /") would mostly
manifest as the app being slow rather than dangerous (we only write inside
the registry root, and only to `skills/` and `.skills-bank/`). Not worth a
hard blacklist; the dialog title and validator are already explicit about
expecting a skills-bank-shaped folder.

### D7. CSP / sandbox for the embedded Discover view

Discover loads `https://skills.sh` in a sandboxed, isolated `WebContentsView`
with a navigation allowlist. We do not inject our own CSP into skills.sh — we
trust its own response headers. If skills.sh ever ships content that we want
to constrain further (e.g., inline-script blocking), we'd need a
`webRequest.onHeadersReceived` interceptor. Not needed today.
