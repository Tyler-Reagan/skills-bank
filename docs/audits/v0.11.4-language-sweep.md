Captures M4's deferred items so the long tail doesn't block release.

## Deferred — internal type/identifier renames (v0.12 candidates)

Per the glossary's flagged-ambiguity note ("the codebase still uses `upstream` as the field name on `SkillSource`; rename or alias for v0.12 if the user-facing rename to **Origin** sticks") — these are internal type or identifier names that should align with the glossary in a future release but carry semantic weight beyond the user-visible layer:

- `SkillSource.upstream` field — rename to `origin` across `@skills-bank/core` and all consumers.
- `UpstreamPointer` type — rename to `OriginPointer`.
- `upstreamUpdateAvailable` field on `RegistryEntry` — rename to `originUpdateAvailable`.
- `DrawerCapabilities.canTakeUpstream` — rename to `canResetToOrigin` (matches the glossary's "Reset to origin" action verb).
- `DrawerCapabilities.canAcceptDrift` — glossary calls the *action* "Unlink origin" but says the capability flag is fine. Leave the flag name; only the action label changed (already shipped in v0.11.2/v0.11.3).
- IPC method names: `upstreamProbe`, `upstreamUpdate`, `upstreamSetManual` — rename to `originProbe`, `originUpdate`, `originSetManual`.
- React action-state names: `"taking-upstream"` → `"resetting-to-origin"`.
- Boolean settings field: `showUpstreamActivity` → `showOriginActivity`.

These should ship as a single coordinated rename PR in v0.12 to keep the diff coherent and the migration reviewable.

## Deferred — naming-analyzer findings

Quick sweep against the renderer surfaced no high-leverage clear wins:

- Single-letter `r` / `s` / `v` in short-scoped IPC response handlers is an established project convention (used consistently across `App.tsx`); the names are narrow-scoped and idiomatic. Forcing `response` / `status` / `value` would add noise without improving readability.
- Boolean state uses a `show*` prefix for modal visibility (`showRegister`, `showSettings`, etc.) rather than `is*`. This is internally consistent and idiomatic React; the glossary doesn't require `is*` for booleans. Forcing `is*` would create inconsistency, not fix it.
- No `data` / `info` / `temp` antipattern identifiers found.
- No misleading function names found in the renderer surface.

The naming-analyzer's "rename script" affordance is **not warranted** for v0.11.4.

## Defer-for-judgement items

The following are stylistic preferences that the maintainer should weigh in on before applying:

- **"Bundled" chip tooltip** currently reads "Skills shipped with the app and managed by Sync." Per glossary, "bundled" overloads to mean (1) shipped-with-app, (2) Sync-managed, (3) the older `bundled-skill-edited` drift state. The chip is filtering by `source.source === "bundled"`, which is sense (2). A more precise tooltip: "Skills curated as part of the bank's bundled set — managed by Sync." Decision: ship as-is or rewrite to "bundled set"?
- **"Yours" chip tooltip** reads "Skills you've added, merged in, or detached from Sync." Mixes three different provenance paths into one chip. Acceptable shorthand, but a curious user clicking the tooltip gets three concepts at once. Possible rewrite: "Skills you authored or unlinked from a curated set." Decision: defer; not a clear win.
