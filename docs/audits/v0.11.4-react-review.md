## Deferred (larger refactors)

These are real but each introduces a new abstraction. Schedule
individually rather than bundle into v0.11.4 polish.

### D1. Extract a `useRescanController` hook from `App.tsx`

The rescan state machine spans **five** locations in `App.tsx`:

- `rescanState` state (L333)
- `userTriggeredProbeRef` (L336) + `doneTimerRef` (L337) with cleanup
  effect (L338-343)
- `onRefreshClick` (L660-681) — sets `working`
- `onUpstreamProbeComplete` subscription branch (L785-807) — advances
  `working → done → idle`
- `viewRescanUpdates` (L872-884) — `done → idle` plus side-effects

Each path mutates timers + refs + state. A `useRescanController` hook
returning `{ state, onRefreshClick, onViewUpdates }` (and internally
listening for `onUpstreamProbeComplete`) would localize the invariants
and make the contract testable. Not done here because it requires
passing `refresh` and `flashError` in, which expands the hook's
surface beyond a clean win.

**Estimated size**: ~80 LOC moved, no new tests required if existing
manual verification stays.

### D2. Context for `flash` + `refresh` + app-error plumbing

`flash`, `refresh`, `pushAppError`, and `flashError` are threaded as
props through nearly every action callback in App.tsx — 2316 lines
of one component, much of it because these four helpers can't be
imported from anywhere. The audit counted **>40** call sites for
`flash` and **>30** for `refresh` inside App.tsx alone, plus the
prop-drilling cost into children (BrowseTab, drawer, modals).

A `<RegistryHostContext>` exposing `{ flash, flashError, refresh,
pushAppError, dismissAppError }` would let leaf components consume
directly. The unblock is non-trivial because `flash` depends on
`toastTimerRef` and `setToast` (which live in App.tsx as the toast
owner) — moving the toast renderer into the provider component is
the prerequisite.

**Estimated size**: ~150 LOC churn (mostly mechanical drop of props),
plus a new provider component.

### D3. Component split for App.tsx (2316 lines)

The component-size threshold from the reviewer rubric is 300 lines;
App.tsx is 7.7× over. The natural seams:

- `<RegistryHost>` — registry/installed state, refresh, sync, repo picker
- `<UpdateHost>` — auto-update state machine + UpdateNotesModal
- `<ToastHost>` — toast state + flash/flashError (overlaps with D2)
- `<ConflictHost>` — every conflict modal + delete confirmation
- `<DrawerHost>` — the giant IIFE around `<SkillDetailDrawer>` and its
  capability-gated callbacks (L2021-2278)

Splitting these is gated on D2 (context for shared helpers). Without
D2, the splits would just re-introduce prop-drilling.

## Other observations (no action proposed)

- **No `any` leaks found** in the reviewed surface. `import("@skills-bank/core").X` inline
  type references in App.tsx (L162, L165, L175, L209, L278, L1964) are stylistically odd —
  hoisting them to top-level `import type { ... } from "@skills-bank/core"` would tidy
  imports but doesn't affect behavior. Skipped to keep this PR scoped.
- **`useEffect` audit**: no effects-as-event-handlers found, no
  missing-cleanup leaks, no missing dep-array entries that aren't
  explicitly annotated with `eslint-disable-next-line` and justified.
  The one annotation (App.tsx:410, overlay reconciliation) is
  correctly classified as "inputs to validate, not deps".
- **React 19 patterns**: `use()`, `useActionState`, and `useOptimistic`
  could in principle apply (e.g. UpdatesModal's per-row `RowState` is
  optimistic-shaped) but the current code is clear and the upgrade is
  not a clear win without changing observable behavior (animation
  timing, error handling). Park for a dedicated React 19 adoption pass.
- **`UpdatesModal`'s `updateAll` loop comment** (L51-57) correctly
  documents the closure-capture pitfall around `states` inside a
  `for` loop. Don't simplify.
